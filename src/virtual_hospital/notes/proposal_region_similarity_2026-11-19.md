# 제안: 슬라이드 1장으로 병리 유사 환자 찾기 (부위 단위)

작성: 2026-11-19 (A) · 상태: **제안** (모듈 2·4-B 담당과 상의 뒤 만든다) · 관련: `src/virtual_hospital/db.py`, `db_schema.sql`, [module_result_format_proposal.md](module_result_format_proposal.md)

## 1. 하려는 것

환자 한 명의 H&E 슬라이드 **1장**을 넣으면, 가상 병원 DB(1,634장)에서 **병리 모양이 비슷한 환자**를 찾고, 입력 슬라이드의 **어느 부위**가 그 환자의 **어느 부위**와 비슷한지 보여 준다.

| 입력 | 예 | 필요한 것 |
|---|---|---|
| ① DB에 있는 환자의 슬라이드 | `VH-B0002-S1` (시험, 화면 시연) | 없음. 그 슬라이드의 부위 벡터가 DB에 있음. 자기 자신은 결과에서 뺌 |
| ② DB에 없는 새 슬라이드 | 다른 병원 슬라이드 파일 | 모듈 1·2와 같은 설정으로 타일 자르기 + H-optimus-0 (GPU) → 타일 벡터 `.h5` → 이후 ①과 같음 |

## 2. 지금 있는 것 (2026-11-19)

| 자료 | 위치 | 슬라이드 | 타일 | 형식 |
|---|---|---|---|---|
| TCGA 타일 벡터 (모듈 1) | GPU 서버 `team_project_final/data/sj/tcga_all/features` | 1,039 (가상환자 663명) | 754만 개, 종양 160만 | H-optimus-0 1,536차원 float16, 타일 512px, 0.25µm, `tumor_tile` 표시 |
| BCNB 타일 벡터 (모듈 2) | GPU 서버 `bcnb-ln-module2/outputs/features_hoptimus0` | 1,058 (가상환자 971명) | 106만 개 | H-optimus-0 1,536차원 float16, 패치 256px → 입력 224, 배율 미상, 종양 표시 없음 |
| 슬라이드 벡터 (타일 평균 1개) | DB `slide_embeddings` (각자 만드는 `local/virtual_hospital.db`) | 1,634 | — | `db.similar(slide_id)`: 슬라이드 단위 검색은 이미 됨 |

- BCNB 타일 좌표는 jpg 원본 픽셀 기준이고, 가상 병원이 정리한 종양 주석 다각형(`local/bcnb/images/annotations/`)도 같은 좌표계다 → 주석 안 타일을 종양 타일로 표시할 수 있다.
- 슬라이드 평균 벡터는 슬라이드 전체를 하나로 뭉개서, "어느 부위가 비슷한지"를 알 수 없다.

## 3. 왜 타일을 그대로 비교하지 않나

- 종양 타일만 모아도 약 270만 개 × 1,536차원 = 약 8GB. 입력 슬라이드의 종양 타일 수천 개를 이와 하나하나 비교하면 보통 컴퓨터에서 한 번에 수 분이 걸린다.
- 타일 벡터 전체(약 37GB)를 조원마다 받기도 어렵다. BCNB에서 만든 벡터는 약관상(수정본 재배포 금지) 조원끼리 나눌 수도 없다.

## 4. 제안: 슬라이드마다 부위 대표 벡터

```
슬라이드 1장의 종양 타일 ──(비슷한 타일끼리 묶기, k-means)──▶ 부위 최대 32개
   부위마다: 대표 벡터 1개(1,536) + 타일 수 + 중심 좌표 + 둘레 상자 + 속한 타일 좌표

입력 슬라이드 → 같은 방법으로 부위 최대 32개
   → DB 부위 약 5만 개(1,634장 × 최대 32)와 cosine 비교 (0.1초 안팎)
   → 입력 부위별 가장 비슷한 DB 부위 (위치 포함)
   → 환자별로 모아 순위 (입력 부위 크기로 가중)
```

| 추가할 것 | 내용 | 크기 |
|---|---|---|
| DB 표 `region_prototypes` | slide_id, 묶음, 부위 번호, 타일 수, 중심 x·y, 둘레 상자, 대표 벡터 | 약 5만 행, 약 150MB |
| `local/features/<묶음>_regions.npz` | 부위마다 속한 타일 좌표 (화면에 부위를 겹쳐 그리기) | 수십 MB |
| `embed_slides.py --regions` | GPU 서버에서 부위 묶기 (타일 벡터가 있는 곳에서 돌리고 결과 파일만 받음) | — |
| 함수 | `db.similar_regions(con, slide_id=… 또는 query_h5=…)`, `db.similar_patients(con, …, k=10)` | — |

선택: 순위 상위 몇 명만 서버에서 타일 벡터 전체를 받아 타일끼리 맞대 보는 히트맵 ("어디가 비슷한지"를 화면에 보여 줄 때만).

## 5. 상의할 것

| 번호 | 질문 | 제안 | 대상 |
|---|---|---|---|
| 1 | 부위를 몇 개로 묶나 | 슬라이드당 최대 32개, 부위당 최소 20타일 (종양 타일이 적으면 줄임) | 4-B |
| 2 | 종양 타일만 쓰나 | 종양 타일만. TCGA는 `tumor_tile`, BCNB는 종양 주석 안 타일 (주석이 없으면 전체) | 2, 4-B |
| 3 | TCGA(수술 검체)와 BCNB(생검)를 섞어 찾나 | **섞지 않음.** 타일 크기·배율·검체 종류가 다르다. 입력과 같은 방식으로 만든 묶음 안에서만 | 1, 2, 4-B |
| 4 | 새 슬라이드(②)의 타일 자르기 설정 | DB 묶음과 같게: 수술 검체면 모듈 1 (512px, 0.25µm), 생검이면 모듈 2 (256px → 224) | 1, 2 |
| 5 | BCNB 배율 | BCNB jpg에 배율 정보가 없다. 다른 병원 생검과 비교할 때 어긋날 수 있음 | 2 |
| 6 | 비슷함을 어떻게 셀까 | 부위 벡터 cosine. 환자 점수 = 입력 부위마다 가장 비슷한 DB 부위 유사도의 가중 평균 | 4-B |
| 7 | 결과 형식 | 모듈 결과 형식 제안(`predictions`, `attention`, `renders`)에 맞출지, 4-B 전용 `neighbors: [{slide_id, region, similarity}]`로 둘지 | 4-B |
| 8 | 타일 벡터 전체의 자리 | 서버에 두고 필요한 환자만 받기 (BCNB는 약관상 공유 불가) | 전원 |

## 6. 만들 때 확인할 것

- 입력이 DB 슬라이드면 자기 자신이 1등으로 나오지 않는지 (같은 환자 제외)
- 같은 환자의 다른 슬라이드(TCGA는 환자당 여러 장)가 결과를 채우지 않는지
- 부위 위치가 슬라이드 크기 안인지 (검증 V6와 같은 검사)
- 미래 값(수술 림프절 결과 등)이 검색에 들어가지 않는지: 검색은 슬라이드 벡터만 쓴다
